## What was built

**1. `Fast_Fetch/domain_resolver.py` — full rewrite (36,829 bytes), old public API preserved.** `resolve_site()` runs the §3 discovery chain cheapest-first, stops at the first content-verified hit: (1) cached `active_base_url`, (2) redirect-follow (inside the probe), (3) known mirrors, (4) bookmark domain, (5) GitHub JSONs (1h in-process cache, shared), (6) TLD probe (site's own history first, then ≤12 generic, www variants, site prefixes, numeric patterns), (7) sister cross-links from pages fetched in steps 1–6, (8) DuckDuckGo search (1 query, ≤3 hosts), (9) Telegram `t.me/s/<verified channel>`, (10) give up → status `down`, NEVER write a guessed domain. `verify_candidate()` (pure, testable): wp-json needs a JSON list ≥1 post, link host == candidate/final host, ≥1 of the first 3 titles carries a quality marker, NO title matches IPTV spam markers; sitemap needs ≥10 same-host locs (≥2 if `<sitemapindex>`); homepage needs ≥2000 bytes, title contains the slug, ≥3 internal links; rejects parked markers, hijack, CF challenge (403/503 + "Just a moment" → reason `cloudflare-challenge`, caller records `unverifiable` not dead). `fetch_url()` (8s timeout, 200KB read cap, IncompleteRead partial body used, HTTPError returns code+body, no SIGALRM — importers run it in threads). `resolve_if_dead()` — after a 0-post sync, probe the cached base once: healthy → `""` (nothing new, no retry); dead → run the chain. `probe_site()` reimplemented content-verified (`domain_shifted` now vs the registry's active base). `probe_all_sites(only_stale=...)` with 6h TTL skip. Constants: PROBE_TIMEOUT 8, READ_CAP 200_000, PROBE_DELAY 0.2, VERIFY_TTL_SECONDS 6h, GITHUB_CACHE_SECONDS 3600, MAX_TLD_PROBES 20, MAX_NUMERIC_PROBES 24 (raised from 12 — with www variants, 12 probes only covered filmyzilla 70–75; live is 80), MAX_SEARCH_PROBES 3, MAX_SISTER_PROBES 5, KNOWN_MIRRORS_CAP 8. ## The geekextreme false positive — caught live, fixed, regression-tested

The first VM run resolved hdtvb to `https://www.geekextreme.com` (verified_by sitemap, 28.2s). That is a tech blog ("GeekExtreme | Geek Culture, Gaming, Gadgets & Tech Since 2000"), NOT hdtvb content — a FALSE POSITIVE, caught before anything was merged (the run wrote only to the /tmp registry copy).
- **Root cause (two holes, one path):** (1) `ddg_search` ranked slug-matching hosts first but ALSO returned non-slug hosts, and step 8 probed up to 3 of them — DDG returned geekextreme.com for the "hdtvb new domain" query. (2) `verify_candidate`'s hijack check only fired when the final host differed from the candidate host (`final_host != cand_host`); here candidate == final == geekextreme.com, so the check never ran, and the sitemap branch (sitemapindex, 19 same-host locs) passed with NO slug check at all.
- **Fix (this session):** `verify_candidate` now rejects unconditionally when the final host carries no site slug — `host-no-site-slug:<final_host>` — no matter how the candidate was reached (this is what design §5 already said: "Reject immediately: final host lacks every site slug"). `ddg_search` now returns slug-matching hosts ONLY. The old `redirect-to-unrelated` reason is gone; the hijack test was updated to the new reason.
- **Regression tests (3 new, 36 → 39):** `test_sitemap_on_unrelated_host_rejected` (geekextreme sitemapindex fixture), `test_ddg_returns_slug_hosts_only`, `test_ddg_unrelated_host_never_verifies` (end-to-end: dead cache/mirrors/TLD + DDG returning the unrelated host → `""`, base kept, status down). One existing fixture had to be corrected, not weakened: `test_wp_no_quality_marker_rejected` used placeholder host `example.test` (no slug) for candidate+final URL, which the new check now rejects first — the fixture now uses the slug host throughout, so the test still proves the quality-marker rejection.
- **Re-probe proof (VM, 14:55 PKT, fixed resolver, fresh registry copy):** hdtvb → `""`, base stays `https://hdutv.com`, status `down`, known_mirrors unchanged, 19.5s. geekextreme.com never verified.
- **Workspace registry:** hdtvb was NOT updated from the bad run — it stays `retired` / `https://hdutv.com`, with only `last_checked` refreshed to the re-probe time (2026-11-08T09:55:08Z). The bad VM registry copy is kept as evidence (`domain-tracker-vm-registry-after-20261108.json` in hidden_files) and must NOT be copied over the workspace registry.
