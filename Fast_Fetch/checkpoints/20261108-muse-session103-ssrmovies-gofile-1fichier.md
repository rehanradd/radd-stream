## Resolver evolution (user directions 04:51 + 04:52 PKT)

1. Stage-2 failover negative-cache pre-filter (Session 102 regression fix, LANDED): in the Stage-2 general failover ladder, after fetching _same_release + _cross_release, one query fetches fresh records among those ids (last_failed_at > now_ts - NEGATIVE_CACHE_TTL_SECONDS); recorded siblings are dropped from the loop; when every sibling is recorded the ladder returns at once with {"success": False, "code": "no_playable_source", "reason": "all_siblings_negative_cached", "stale": True}. Unrecorded siblings are still tried in full (Session 102 F1 preserved); they earn their own record when they fail. If the cache query throws, falls back to the old list (fail-open). Analysis: the per-sibling record check already existed inside the recursive resolve_live_source — the 9–12 s repeat cost was the ladder re-probing UNRECORDED siblings (~1 s cached probe each) up to the 10 s budget on every press; the list self-exhausts after ~3 presses, but the pre-filter makes the all-recorded case an explicit one-query refusal. Stage-1 sibling failover (resolve_release) does NOT consult the cache — out of scope here; flag if it ever shows the same symptom. Mechanism PROVEN: unit test passes; isolated VM repro (/tmp/vm103-alldead.py on the VM, fresh fixture DB) returns all_siblings_negative_cached in 0.02 s; and the full-harness run (/tmp/vm103b-proof3.py) returns it in 0.0 s through the real resolver. The earlier 04:27 VM proof run returned stale_probe_failed in 1.67 s instead — investigated ~04:53 PKT: workspace code and the VM copy were byte-identical (diff empty, both 360,897 B), and a local repro of the same fixture returns all_siblings_negative_cached in 0.01 s, so the 04:27 anomaly was a stale-fixture artifact of that particular run (its fixture DB was built by a harness invocation that had crashed once on a posts.url IntegrityError and been re-run), not a code bug. The 0.02 s isolated repro is the authoritative live measurement.
2. Host health scoring (audit Phase A item 6, LANDED): in-process only — _host_failures: dict[str, list[float]] (per-service failure timestamps, pruned to last hour), _HOST_HEALTH_WINDOW_SECONDS = 3600.0, _HOST_HEALTH_DEMOTE_AFTER = 3, _note_host_failure(service) + _host_failure_count(service). _record_resolve_failure now does a PK lookup (SELECT service FROM download_sources WHERE id =?) after its UPDATE and notes the service — one cheap read on the failure path only, never on success. The Stage-2 ladder, after the pre-filter, does ONE bounded PK query (SELECT id, service... WHERE id IN (...)) over its own candidate ids and demotes services with >=3 recent failures to the back, preserving order inside each group; a service below the threshold is never reordered. Why in-process, not global: download_sources has NO index on service or last_failed_at (indexes are only idx_sources_rel (release_id), idx_sources_res (resource_id), idx_sources_status_temp (status, is_temporary), idx_sources_rel_status (release_id, status)) — a global per-service fresh-failure count would full-scan the 4M-row ledger per service. Adding an index is a heavy live-DB migration (same reason the is_resumable CREATE INDEX is still a separate careful sub-step) — NOT done here. Tests: test_host_health_demotes_a_repeatedly_failing_service (sick sibling first by id — created_at forced equal so the tiebreak is id ASC — but healthy sibling served, sick never probed, 2 probes) + test_host_health_below_threshold_does_not_reorder (2 failures -> first sibling still wins). Both clean up _host_failures in a finally (module-level state persists across tests in the process).
